# QingYan Admin Console And Captcha Threshold Design

## 背景

当前 `QingYan` 已经具备后台管理相关 API，包括管理员登录、评论管理、黑名单管理和运行时设置，但仓库里还没有浏览器可直接使用的后台管理页面。

联调还暴露出一个实际语义偏差：`thresholdMaxActions` 目前在代码与测试中的解释更接近“允许写入次数上限”，而配置和人类理解更接近“从第几次开始要求验证码”。当配置值为 `3` 时，当前实际行为与预期表述存在偏差，需要统一。

## 目标

1. 修正验证码阈值语义，让 `thresholdMaxActions = N` 明确表示“从第 `N` 次写操作开始要求验证码”。
2. 在当前仓库内新增一个最小可用的同源后台管理页面，浏览器访问 `/admin` 即可使用。
3. 后台页面复用现有管理员会话 API 和 `qingyan_admin` cookie，不引入第二套认证体系。
4. 后台页面至少覆盖登录、评论管理、黑名单管理和运行时设置四项真实能力。

## 非目标

- 不引入多管理员账号体系。
- 不引入角色权限、细粒度 RBAC 或审计视图。
- 不新增第二套 admin API、BFF 或 GraphQL 层。
- 不把当前仓库升级成独立前后端双应用工程。
- 不在本轮内扩展新的仪表盘统计接口。
- 不让 admin 端复用公开写入链路中的验证码或黑名单策略。

## 核心决策

### 1. 管理后台采用同源 `/admin`

后台页面直接由当前 Fastify 进程提供，路径为 `/admin`。静态资源和页面入口都在本仓库内构建并随服务一起提供。

选择该方案的原因：

- 最贴合当前 `QingYan` 的“后端仓库”形态。
- 不需要再引入前端 dev server、跨域配置或额外部署单元。
- 最容易复用现有管理员会话 cookie。

### 2. 认证流完全复用现有 admin session API

浏览器打开 `/admin` 时，先请求 `GET /api/admin/session/me` 做会话探测：

- 返回 `200`：进入后台壳层，使用返回的 `sites` 初始化站点切换。
- 返回 `401`：显示登录页。

登录表单提交到 `POST /api/admin/session/login`，成功后由后端设置 `qingyan_admin` cookie，前端不持久化 token。登出调用 `POST /api/admin/session/logout`，然后回到登录页。

### 3. admin 端不触发验证码和黑名单逻辑

管理后台属于独立的管理员操作面，不复用公开评论 / 投票 / 页面点赞写入链路中的验证码与黑名单拦截策略。

明确规则如下：

- `/admin` 页面登录与后台管理请求不触发验证码流程
- 后台管理请求不走公开访客黑名单拦截逻辑
- admin 端权限边界仅由 `admin.tokenHash` 登录和 `qingyan_admin` session cookie 控制

这条规则同样适用于后台页面本身与其调用的 admin API，避免出现“管理员被评论侧验证码或访客黑名单挡住”的行为。

### 4. 阈值语义统一为“第 N 次开始触发”

统一定义如下：

`thresholdMaxActions = N` 表示“从第 `N` 次写操作开始要求验证码”。

以 `N = 3` 为例：

- 第 1 次写操作：允许直接通过
- 第 2 次写操作：允许直接通过
- 第 3 次写操作：开始要求验证码

文档、后台设置页文案、测试名和后端实现都必须使用这一套表述，避免“允许 N 次后触发”和“第 N 次开始触发”并存。

## 页面与信息架构

### 登录页

登录页保持极薄：

- 一个 `Admin Token` 输入框
- 一个登录按钮
- 一个错误消息区域

登录失败只显示后端统一错误消息，不额外暴露内部细节。

### 后台壳层

登录后进入统一后台壳层，采用左侧导航 + 右侧工作区：

- 左侧顶部：当前站点切换
- 左侧导航：评论管理 / 黑名单 / 运行时设置
- 右侧：当前页面内容

默认页为“评论管理”，因为这是最高频、也最依赖列表筛选和操作反馈的后台功能。

### 评论管理页

评论管理页复用现有接口：

- `GET /api/admin/comments`
- `PATCH /api/admin/comments/:commentId`
- `DELETE /api/admin/comments/:commentId`

最小首版能力：

- 按站点查看评论
- 支持基础筛选：`status`、`pageKey`、`search`
- 列表展示关键字段：作者、页面、内容、状态、时间
- 支持审核 / 置顶 / 折叠 / 删除
- 操作完成后做局部刷新，不整页重载

### 黑名单页

黑名单页复用现有接口：

- `GET /api/admin/blacklist`
- `POST /api/admin/blacklist`
- `DELETE /api/admin/blacklist/:ruleId`

最小首版能力：

- 查看当前站点黑名单规则
- 新增规则
- 删除规则

### 运行时设置页

设置页复用现有接口：

- `GET /api/admin/settings`
- `PUT /api/admin/settings`

首版至少包含以下高价值字段：

- 评论默认状态
- 验证码模式
- 验证码阈值窗口
- 从第几次写操作开始要求验证码
- 页面点赞开关

设置页里的 `thresholdMaxActions` 字段文案必须显式写成“从第 N 次写操作开始要求验证码”或等价中文，不再使用“允许多少次后触发”表达。

## 前端实现边界

本轮只做一个轻量后台壳，不引入重量级前端架构。

建议结构：

- 一个 `admin-app` 入口脚本
- 一个共享的最小 API 请求封装
- 三个页面模块：评论、黑名单、设置
- 一个会话 / 站点 / 当前标签页的轻量状态容器

不引入全局状态管理库，不引入复杂组件系统，不增加新的构建目标之外的运行单元。

## 静态资源与服务端集成

后端需要新增一条与 `/docs` 平行的页面能力，用于提供 `/admin` 页面和其静态资源。

预期集成方式：

- 构建产物进入仓库已有的 `dist` 体系
- 运行时由 Fastify 提供 `/admin` 和关联静态资源
- 页面与 API 保持同源

该集成只为管理后台服务，不改变现有公开 API 路由结构。

## 数据流与状态流

后台前端遵循统一流程：

1. 启动时获取 session
2. 根据 session 决定显示登录页还是后台壳层
3. 进入后台后按当前站点和当前标签页加载数据
4. 写操作完成后重新拉取当前页所需数据

局部页面状态最小化：

- 评论页：筛选条件、分页参数、当前列表、操作中状态
- 黑名单页：列表、创建表单、提交状态
- 设置页：表单值、保存状态、保存反馈

## 错误处理

### 会话探测

- `/api/admin/session/me` 返回 `401` 时，前端仅视为“未登录”
- 不弹全局错误

### 后台工作区中的会话失效

如果后台工作区内的管理请求返回 `401`：

- 清空当前页面数据状态
- 回退到登录页
- 给出“登录已过期，请重新登录”的用户提示

### 管理操作错误

评论、黑名单、设置的写操作统一采用：

- 提交中
- 成功提示
- 失败提示
- 局部刷新

失败提示优先复用后端已返回的统一错误消息。

### admin 侧安全边界

admin 侧不走公开写入链路中的验证码和访客黑名单策略，因此实现时需要明确分开两类逻辑：

- 公开评论侧安全逻辑：验证码、访客黑名单、访客频率限制
- 管理后台安全逻辑：admin token 登录、admin session 校验、admin login 限流

管理员后台仍然保留已有的 `adminLogin` 失败限流逻辑，但这属于管理员登录保护，不属于评论侧验证码 / 黑名单链路。

## 验证码阈值修正设计

当前问题位于验证码阈值判定逻辑及其测试表达方式。

修正后的行为要求：

- 在 threshold 模式下，没有活动验证码会话时，系统先根据当前写操作序号判断是否应触发验证码
- 若当前写操作尚未达到 `thresholdMaxActions`，允许通过并计入计数
- 若当前写操作达到 `thresholdMaxActions`，本次请求直接返回“需要验证码”，并创建 challenge
- 用户完成验证后，后续对应页面写操作可继续通过，直到 challenge 生命周期结束或新一轮阈值判断再次触发

需要一起收口的地方：

- `captcha-service` 内部判断条件
- 对应 integration tests
- 配置文档
- 后台设置页字段文案
- admin 页面和 admin API 的实现边界，确保不会误接入公开验证码 / 黑名单链路

## 测试策略

### 1. 后端语义修正测试

先修改现有 integration tests，使其明确表达新语义：

- `thresholdMaxActions = 3` 时，第 1、2 次写操作通过
- 第 3 次写操作开始要求验证码

测试先失败，再修改实现到通过。

### 2. 后台页面验证

首版不引入重型 e2e 基建，但必须有最小可依赖验证：

- 访问 `/admin` 未登录时显示登录页
- 使用 admin token 登录后进入后台壳层
- 已登录状态可以加载站点与默认页
- 评论、黑名单、设置三个页面至少各有一条真实 API 联动 smoke
- 构建产物可被 Fastify 正常提供，浏览器可直接访问 `/admin`
- admin 页面联调过程中不会触发公开验证码或访客黑名单逻辑

### 3. 回归验证

完成后需要继续保证：

- 现有 admin API 测试通过
- 评论、投票、验证码相关回归测试通过
- 构建通过

## 验收标准

完成后应满足以下结果：

1. 配置 `thresholdMaxActions = 3` 时，联调行为为“第 3 次开始要求验证码”
2. 浏览器访问 `/admin` 可看到后台登录页
3. 使用 admin token 可登录后台
4. 登录后可管理评论、黑名单和运行时设置
5. admin 端登录与管理操作不触发公开验证码和访客黑名单逻辑
6. 设置页中的阈值字段语义与后端真实行为一致
7. 相关自动化验证通过
